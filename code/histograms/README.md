# Гистограммы проекта

Поиск пассажиров по выбранному X для всех пассажирских гистограмм находится в
[`search_users/`](search_users/README.md). Меняйте `SELECTED_X` в нужном
`find_*.py` и запускайте `search_users/run_all_user_searches.py` или
`<project>\run_user_search.cmd`. Отдельные TXT сохраняются в `results/user_search/`.

## Python и зависимости

Для этого проекта подготовлена среда `<project>\.venv` на основе установленного
Python 3.13 с доступом к его пакетам (`--system-site-packages`). Ничего скачивать
для текущего запуска не требуется. В PyCharm выбирайте интерпретатор
`<project>\.venv\Scripts\python.exe`; у конфигурации `run_all_passenger_metrics`
этот путь уже задан. Если PyCharm сохраняет старую настройку в открытом окне,
укажите этот путь в конфигурации запуска вручную.

Двойной щелчок по `<project>\run_histograms.cmd` запускает все пассажирские гистограммы.
Надёжный запуск из PowerShell в `<project>`, независимо от настроек `python` и `py`:

```powershell
.\.venv\Scripts\python.exe code/histograms/run_all_passenger_metrics.py
```

Для любого отдельного скрипта меняется только имя файла. В командах ниже
`py` также можно заменить на `.\.venv\Scripts\python.exe`.
На другом компьютере с установленным обычным Python создайте среду и установите
зафиксированные зависимости (понадобится интернет):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Все команды ниже запускаются из `<project>`. Для отдельных скриптов `SHOW_WINDOW = True`
открывает интерактивное окно Matplotlib. Панель позволяет приближать и сохранять
график. Результаты всегда сохраняются в этой папке, в `results/`.

Если база занята просмотрщиком, сначала запустите `закройте приложение, которое держит файл базы`.

## Общий запуск пассажирских гистограмм

Сразу пересчитать все метрики и сохранить десять графиков:

```powershell
py code/histograms/run_all_passenger_metrics.py
```

Этот запуск использует одно соединение с базой и открывает все десять графиков в интерактивных
окнах Matplotlib. `SHOW_WINDOW = False` оставляет только сохранение файлов.
Это восемь графиков новых метрик (максимум активности отдельно для 7 и 30 дней),
а также число перелётов и число перелётов с признаком багажа по уникальным билетам.
У всех есть Q1/Q3; у числа перелётов сохранён доверительный интервал среднего.
База закрывается до открытия окон. Значение `SHOW_WINDOW` в общем скрипте
управляет всеми десятью окнами; при отдельном запуске действует настройка своего скрипта.

Две ранее созданные гистограммы сохраняются в прежних папках:
`results/passenger_flight_counts/` и `results/passenger_baggage_counts/`.
Их отдельные скрипты и поиск пассажиров по X продолжают работать.

| Скрипт (запуск `py code/histograms/имя.py`) | Показатель на X | Настройка |
| --- | --- | --- |
| `count_unique_routes.py` | Число уникальных направленных пар аэропортов | — |
| `count_max_flights.py` | Максимум перелётов за окно | `WINDOW_DAYS = (7, 30)` |
| `count_min_flight_interval.py` | Минимальный промежуток между вылетами, часы | — |
| `count_route_repetitions.py` | Число перелётов по самому частому маршруту | Первый перелёт включён |
| `count_quick_returns.py` | Число последовательных возвращений A → B → A | `RETURN_HOURS = 48` |
| `count_airlines.py` | Число кодов перевозчиков | Двухсимвольный код из номера |
| `count_loyalty_cards.py` | Число известных карт лояльности | Программа + номер |

На Y — число пассажиров (документов). Если по X много разных значений,
они объединяются в интервалы. Q1 и Q3 рассчитаны по индивидуальным значениям
всех пассажиров с оценкой, с одинаковым весом документа и линейной интерполяцией.
NULL означает «недостаточно данных»; он не превращается в ноль и не входит в квартили.
Количество исключённых документов указано на графике и в JSON.

Результаты: `results/passenger_metrics/<метрика>/`:

- `passengers.csv` — документ, ФИО, показатель и полнота данных;
- `distribution.csv` — точное распределение, без группировки в интервалы;
- `statistics.json` — Q1, Q3, число документов с оценкой и без неё;
- `histogram.png` — готовый график;
- `details.csv` — подтверждающие поездки/маршруты/карты, когда применимо.

`input_audit*.json` содержит число неоднозначных связей и пропусков.
`card_links.csv` сохраняет происхождение каждой связи документа с картой.

## Как сопоставляются поездки

Общий код — `passenger_metrics_common.py`, подготовка данных —
`prepare_passenger_metrics.sql`. Для перелётов используются три таблицы:

```text
boarding_data: PassengerDocument -> TicketNumber, FlightNumber, FlightDate, FlightTime
sirena: TravelDoc -> e-Ticket, Flight, DepartDate, DepartTime, From, Dest
boarding_passes: e_ticket -> flight_number, raw_date, flight_time, from_iata, to_iata

merge:
PassengerDocument = TravelDoc
TicketNumber / e-Ticket = boarding_passes.e_ticket
```

Документы и билеты остаются строками, пробельные символы удаляются, регистр
нормализуется; маркеры отсутствия исключаются. Имя используется только для вывода.
Если билет связан более чем с одним документом, через него не присоединяются
посадочные талоны. Прямые записи BoardingData и Sirena сохраняют свои документы.

Перелёт = документ + номер рейса + дата + время. Повторы удаляются.
Разное время в один день считается разными перелётами. Запись без времени
учитывается один раз, только если для того же документа, номера и даты нет времени.
Номер и дата обязательны. Разногласия времени могут завышать счётчики.

Если для документа, номера рейса и даты найден ровно один маршрут, он дополняет
записи этого дня. При конфликте маршрутов он остаётся неизвестным; произвольный
вариант не выбирается. Коды аэропортов проверяются по формату из трёх букв,
по внешнему справочнику не проверяются. A → A не удаляется из исходных маршрутов,
но не считается быстрым возвращением. A → B и B → A — разные маршруты.

Перелёты форума, Pointz и SkyTeam не присоединяются по имени или только номеру рейса:
для этих новых метрик используется описанная связь документа с билетом.

## Особенности метрик

- Окно активности — 7 или 30 календарных дат в местных датах источника,
  `[начало, начало + N дней)`. Несколько вылетов за день учитываются отдельно.
  В `details.csv` сохранено одно окно, достигающее максимума.
- Минимальный промежуток требует минимум двух перелётов и известного времени
  всех учтённых вылетов. При одновременных разных рейсах минимум может быть нулевым.
- Быстрые возвращения требуют полной последовательности: минимум два перелёта,
  время и однозначный маршрут всех учтённых перелётов, отсутствие совпадающего
  времени вылета. Берутся только соседние обратные маршруты, каждый перелёт
  используется один раз, `0 < интервал <= RETURN_HOURS`.
- Интервалы считаются между вылетами по местным часам. Часовые пояса не известны,
  поэтому это предварительные показатели, а не точное время пересадки или пребывания.
- Без известного маршрута уникальные маршруты и повторения дают NULL.
  Без известного перелёта с датой максимум активности даёт NULL.
- Коды авиакомпаний выделяются из номеров вида `SU123`, `S7123`, `3U123`.
  Это код в номере, не обязательно фактический оператор. Нераспознанные номера
  не дают код; без распознанных кодов оценка NULL.

## Карты лояльности

В `prepare_loyalty_metrics.sql` извлекаются `FF#<программа> <номер>` из
`sirena.PaxAdditionalInfo` и связываются напрямую с `TravelDoc`.
Затем карты сопоставляются с `forum_loyalty` по `profile_id` и с Pointz по `uid`.
Профиль используется только если его прямые карты указывают на один документ
и ни одна из этих карт не имеет нескольких владельцев.

Программы Pointz приводятся к кодам данных: Aeroflot Bonus → SU,
Flying Blue → FB, Korean Air SKYPASS → KE, Delta SkyMiles → DT.
Поддерживаются цифровой номер и номер с уже добавленным кодом программы.
Дополнительные карты профиля добавляются за один шаг, без цепочки догадок.
Если дополнительная карта приводит к нескольким документам, косвенная связь
исключается; прямые свидетельства Sirena сохраняются для каждого документа.
SkyTeam не даёт новых связей документа с владельцем, поэтому не расширяет список.
0 означает «не найдено известных карт», а не «карт нет».

## Прежние графики

Прежние скрипты и их SQL перенесены сюда с сохранением настроек пользователя:

```powershell
py code/histograms/count_passenger_flights.py
py code/histograms/count_passenger_baggage_flights.py
py code/histograms/count_flights_by_number.py
py code/histograms/count_flight_routes.py
py code/histograms/count_flights_by_location.py
py code/histograms/plot_flight_counts.py
```

Их результаты также находятся в `code/histograms/results/`. Подробности прежних
настроек — в [EXISTING_SCRIPTS.md](EXISTING_SCRIPTS.md).
Для анализа выбросов превышение Q3 само по себе не является критерием:
обычная верхняя граница — `Q3 + 1.5 * (Q3 - Q1)`. При Q1 = Q3 этот критерий
может быть малоинформативным, особенно для редких событий.
